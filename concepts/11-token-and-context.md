# Token 和上下文：大模型一次能看多少内容

在学习 Prompt、RAG 和 Agent 时，我经常会遇到两个词：**Token** 和 **Context（上下文）**。

我现在会用一个简单的比喻来理解它们：

> **Token 是模型处理文字时使用的一块块积木；上下文是模型这一次可以摆放和参考这些积木的桌面。**

## Token：模型处理文本的单位

人类阅读时，通常会把中文理解成字、词，把英文理解成单词。但模型处理文本时，不一定直接使用这些人类熟悉的单位，而是先把文本切分成一段段 Token。

一个 Token 可能是一个汉字、几个汉字、一个英文单词的一部分，也可能是标点、空格或其他字符片段。因此，Token 和“字”或“单词”不是固定的一一对应关系。

例如下面这句话：

```text
帮我查询订单物流
```

模型内部可能会把它切成若干个 Token。具体怎么切，取决于模型使用的分词器，不同模型的切分方式也可能不同。

所以，Token 更准确地说是：**模型进行理解和生成时使用的文本处理单位**。它不一定是一个完整、有独立意义的词。

## 上下文：模型本次能参考的工作空间

上下文不是单纯指用户刚刚输入的那句话，而是模型本次生成回答时能够看到的全部信息。它可能包括：

- 系统指令和开发者要求
- 当前用户 Prompt
- 前几轮对话
- RAG 检索出来的资料片段
- 工具调用的参数
- 工具返回的结果
- 模型这一次准备生成的回答

这些内容都会占用上下文空间。

如果一个模型支持 1000 Token 的上下文，可以把它理解为：这次请求中，模型能够处理的输入和输出总范围大约不能超过这个容量。不同模型和接口的具体计算方式可能不同，但“输入和输出共同受到容量限制”是一个重要的基本概念。

## 输入和输出都会占用上下文吗？

通常都会。可以把一次调用想成这样：

```text
系统指令
+ 当前 Prompt
+ 历史对话
+ 检索资料
+ 工具结果
+ 本次模型回答
--------------------------------
不能超过模型允许的上下文容量
```

如果输入材料已经占用了大部分空间，留给模型生成回答的空间就会减少。因此，很多接口还会提供 `max_output_tokens` 一类的参数，用来限制本次回答最多生成多少 Token。

需要注意：上下文总上限和最大输出长度是相关但不同的概念。模型可能有一个整体上下文窗口，同时接口还会允许你单独设置本次最多生成多少内容。

## 如果超过上下文限制，会发生什么？

常见情况有三种：

1. **请求直接失败**：接口返回上下文超限或输入过长的错误。
2. **应用自动裁剪**：删除较早的聊天记录，只保留最近内容。
3. **应用自动压缩**：把较长的历史对话总结成一段摘要，再把摘要放回上下文。

如果是在生成过程中达到输出上限，回答可能会被截断，表现为话说到一半、JSON 不完整或代码缺少结尾。

大模型本身通常不会自动替应用整理所有历史内容。某个产品如果做了删减、摘要、检索或分层记忆，往往是产品或 Agent 程序在调用模型前后完成的。

## 上下文不是 Chunk

这两个概念很容易混淆。

- **Chunk**：应用把一篇长文档提前切成的小段，方便建立索引和检索。
- **Context**：本次真正发送给模型阅读的全部内容空间。

例如一本产品手册被切成 100 个 Chunk，但用户问一个问题时，RAG 可能只检索出其中 3 个 Chunk，然后把这 3 段资料放进本次 Context。

可以这样看：

```text
完整知识库
   ↓ 预先切块
很多 Chunk
   ↓ 根据问题检索相关片段
少量相关 Chunk
   ↓ 加上 Prompt 和对话历史
本次 Context
   ↓
模型生成回答
```

所以，Chunk 是资料的切分单位；Context 是模型本次实际看到的工作材料。Chunk 可能很多，但不应该把所有 Chunk 一次性塞进 Context。

## 多轮对话为什么不会无限增长？

如果每一轮都把完整历史重新发送给模型，对话越长，占用的 Token 就越多，最终可能超过上下文限制。因此，实际应用通常会对历史内容进行管理。

一个常见策略是：

```text
完整对话历史
       ↓
保留最近几轮原文
       ↓
把较早内容压缩成摘要
       ↓
检索与当前问题相关的 Memory
       ↓
加入本轮 Prompt 和必要资料
       ↓
形成有限大小的 Context
```

例如，客服 Agent 可能保留最近几轮对话原文，同时把较早内容压缩成：

```json
{
  "summary": "用户正在处理订单 A123 的物流问题，已完成身份验证，用户希望收到简短回复。",
  "open_issue": "等待查询最新物流状态"
}
```

这里的摘要帮助模型快速理解历史，`open_issue` 则提示 Agent 当前还有什么事情没有完成。

## 上下文、摘要和 Memory 的区别

它们都和“保留信息”有关，但用途不同：

- **上下文**：本次调用实际交给模型阅读的内容。
- **对话摘要**：对较长历史的压缩版本，帮助减少 Token 占用。
- **Memory**：应用专门保存、未来可能重复使用的偏好或背景。
- **State**：当前任务正在使用的结构化状态，例如订单号、目的地和流程阶段。

比如：

```json
{
  "state": {
    "destination": "东京",
    "budget_cny": 20000,
    "stage": "searching_flights"
  },
  "memory": {
    "travel_preferences": ["喜欢慢节奏", "偏爱美食"]
  },
  "conversation_summary": "用户计划今年秋天去东京，已确认预算，正在查航班。"
}
```

这些数据只有在需要时才会被应用挑选出来，放进本次 Context。模型不是永久自动记住所有内容，而是应用在每次调用时重新组织它能看到的材料。

## 上下文越大就一定越好吗？

不一定。更大的上下文意味着可以放进更多内容，但也可能带来几个问题：

- 输入和处理成本增加
- 响应速度变慢
- 无关内容干扰模型判断
- 关键信息被大量文字淹没
- RAG 检索结果太多，反而降低回答质量

因此，应用设计的目标不是“把所有历史和资料都塞进去”，而是**选择本轮真正相关、可靠、足够的内容**。

## 我的总结

> **Token 是模型处理文字的积木；上下文是本次模型可以使用的桌面；Chunk 是提前切好的资料小纸片；应用程序则负责整理桌面。**

当输入或历史过长时，应用可能裁剪最近内容、压缩旧对话、检索相关 Memory，或者减少本次放入的 RAG 资料。这样做的目的不是让模型永久记住更多东西，而是在有限的上下文空间里，尽量提供对当前任务最有用的信息。
