# Evals：如何判断一个 AI 应用是否真的工作得好

在学习 AI 应用时，我起初以为只要页面能打开、接口能返回结果，系统就算运行正常。后来接触 Evals 才发现，AI 应用还需要检查模型在中间过程中的判断是否正确。

我现在把 Evals 理解成：

> **为 AI 应用准备一组测试样例，规定期望结果，运行系统并比较实际结果，从而评估模型、Workflow 和 Agent 是否按预期工作。**

## Evals 像自动化测试，但不只是自动化测试

传统自动化测试通常关注程序功能是否正常：

- 页面是否可以打开
- 接口是否返回成功
- JSON 格式是否正确
- 数据库是否成功写入
- 工具是否能够执行

这些检查很重要，但 AI 应用还有一些传统程序测试不容易覆盖的地方。比如接口虽然返回了结果，但模型可能把“查物流”误判成“申请退款”，或者在缺少订单号时错误地调用了查询工具。

因此，AI 应用的评测还要关注模型和 Agent 的行为：

- 意图识别是否正确
- Router 是否选中了正确分支
- State 是否更新正确
- 缺少参数时是否追问
- 是否应该调用工具才调用工具
- 工具参数是否正确
- 工具结果是否被正确使用
- 最终回答是否符合业务目标

## 一个售后助手的评测例子

用户输入：

> 帮我查一下 A123 订单有没有发货。

我们可以为这条测试样例规定期望结果：

```json
{
  "input": "帮我查一下 A123 订单有没有发货",
  "expected": {
    "intent": "查询物流",
    "branch": "order_lookup",
    "order_id": "A123",
    "tool_called": true,
    "state_status": "completed"
  }
}
```

系统运行后的实际结果可能是：

```json
{
  "actual": {
    "intent": "查询物流",
    "branch": "order_lookup",
    "order_id": "A123",
    "tool_called": true,
    "state_status": "completed"
  }
}
```

如果这些关键字段符合预期，这条用例就可以通过。

## 缺少参数也应该被测试

用户如果只说：

> 帮我查一下订单有没有发货。

系统不应该直接调用订单工具，因为订单号还没有提供。期望结果应该是：

```json
{
  "input": "帮我查一下订单有没有发货",
  "expected": {
    "intent": "查询物流",
    "branch": "order_lookup",
    "order_id": null,
    "tool_called": false,
    "next_action": "询问订单号",
    "state_status": "waiting_for_user"
  }
}
```

如果系统直接调用了订单查询工具，或者编造了一个订单号，即使页面没有报错，也应该被评测判定为失败。

这说明 Evals 不只是检查“程序有没有运行”，还要检查它在缺少条件时有没有做出正确的业务决策。

## Evals 要检查哪些步骤？

可以把一次 AI 请求拆成几个评测点：

```text
用户输入
   ↓
意图识别：识别对了吗？
   ↓
Structured Output：字段完整吗？
   ↓
Router：分支选对了吗？
   ↓
State：当前状态更新对了吗？
   ↓
Tool Calling：该调用工具吗？参数正确吗？
   ↓
工具结果：结果有没有正确返回？
   ↓
最终回答：是否符合业务要求？
```

例如可以记录成一条 Trace：

```json
{
  "input": "帮我查一下 A123 订单有没有发货",
  "trace": [
    {"step": "intent_detection", "result": "通过"},
    {"step": "router", "result": "通过"},
    {"step": "state_update", "result": "通过"},
    {"step": "tool_arguments", "result": "失败"},
    {"step": "final_answer", "result": "失败"}
  ]
}
```

这样就能知道问题出在工具参数，而不是笼统地说“模型回答错了”。

## Evals 和控制变量

AI 的输出具有一定随机性，因此评测时经常需要控制变量。例如：

- 测试样例保持不变，只更换模型
- 模型保持不变，只调整 Temperature
- Prompt 保持不变，只修改 Router 规则
- Workflow 保持不变，只更换 RAG 检索策略
- 工具返回结果保持不变，只比较最终回答

这样才能更清楚地判断：结果变化到底是由模型、Prompt、采样参数、检索方式还是程序逻辑造成的。

例如同一批测试样例下：

```text
Qwen3 + Temperature 0.2：通过率 92%
Qwen3 + Temperature 0.8：通过率 76%
```

这并不代表低 Temperature 永远更好，但可能说明当前任务是结构化路由，输出稳定性比表达多样性更重要。

## Evals 不一定要求文字完全相同

对于分类或工具调用，通常可以直接比较字段：

```json
{
  "expected_intent": "查询物流",
  "actual_intent": "查询物流",
  "pass": true
}
```

对于开放式回答，则不一定要求每个字都一样，而是检查：

- 是否包含关键事实
- 是否引用了正确的资料
- 是否没有编造信息
- 是否遵守了回答格式
- 是否没有泄露不应透露的内容

例如售后回答可以检查是否包含订单状态，但不应该把语言风格差异直接判定为失败。

## 一组最小评测集应该包含什么？

不要只准备“正常成功”的样例，还要覆盖边界情况：

```text
正常查物流，有订单号
查物流，但缺订单号
退款申请，有订单号
退款申请，缺订单号
投诉或服务反馈
普通咨询
用户表达含糊
用户输入无关内容
工具返回错误
模型输出格式错误
```

这些样例可以帮助我们发现：系统是否只会处理理想输入，一遇到缺字段、错误或歧义就失效。

## Evals 的结果如何使用？

如果评测失败，不应该只看最终答案，而应该结合 Trace 定位问题：

```text
意图识别失败 → 修改分类 Prompt 或增加样例
Router 选择错误 → 修改分支规则
State 没有更新 → 检查状态管理逻辑
工具参数错误 → 加强 Schema 和参数校验
工具失败 → 增加错误处理和重试
最终回答错误 → 检查模型是否正确使用工具结果
```

修复后，再运行同一批测试。如果原来的问题解决了，但其他用例开始失败，就说明出现了回归问题。

## Evals 能保证模型永远正确吗？

不能。Evals 只能说明：在准备好的测试样例和评价标准下，系统表现如何。测试集覆盖不到的输入，仍然可能出问题。

所以需要持续增加测试样例，尤其是从真实使用中发现的失败案例。一次线上错误，就可以转化成一条新的评测用例，避免同类问题再次出现。

## 我的总结

> **Evals 是 AI 应用的质量检查体系。它不只是检查程序是否报错，还要检查模型在意图识别、路由、状态更新、工具调用和最终回答上的行为是否符合预期。**

传统自动化测试关注“程序能不能运行”；Evals 进一步关注“AI 是否做出了正确的判断”。通过固定测试样例、明确评价标准、控制变量和记录 Trace，我们才能逐步把一个会运行的 AI Demo，变成一个更可靠的 AI 应用。
