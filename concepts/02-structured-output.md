# Structured Output：让 AI 按模板整理数据

我现在把 Structured Output 理解成一种“AI 帮忙填写结构化表格”的方式。

## 从 Excel 导入说起

传统的 Excel 导入通常需要先准备好表头或模板，例如：

```text
出发地 | 目的地 | 出行时间 | 天数 | 预算 | 偏好
```

然后由人按照每一列逐项填写。如果信息来自聊天、邮件或一段自然语言，就需要人工阅读内容，再把数据复制到正确的列里。

有了 AI，用户可以直接描述：

> 我从杭州出发，国庆后去成都玩 5 天，预算 8000 元，喜欢美食。

模型可以根据预先定义的字段，把内容整理成 JSON：

```json
{
  "departure_city": "杭州",
  "destination_city": "成都",
  "travel_date": "国庆后",
  "nights": 5,
  "budget_cny": 8000,
  "preferences": ["美食"]
}
```

## JSON 和 Schema 分别是什么？

- **JSON** 是一种常见的数据文本格式，可以用“字段名 + 值”表达信息，也能包含列表和嵌套结构。
- **Schema** 是数据结构的说明和规则，定义有哪些字段、字段类型、哪些必填，以及是否允许额外字段。
- **JSON Schema** 是用 JSON 格式写出的 Schema 规则。

用 Excel 来类比：JSON 像填好的表格数据，Schema 像表头、模板和填写规则。JSON 不是 Excel 或数据库本身，而是程序之间传递数据的一种格式。

## Structured Output 的流程

```text
用户用自然语言描述
        ↓
程序提供字段模板（Schema）
        ↓
模型把描述映射到对应字段
        ↓
输出符合结构的 JSON
        ↓
程序检查数据，再决定是否确认、保存或导出
```

这让用户不必手动逐格填写，系统可以先把自然语言整理成程序容易处理的数据。后续程序可以把数据展示给用户确认、写入数据库，或生成 Excel/Word 文件。

## 常见使用场景

### 1. 从聊天记录中提取信息：自动记账

用户说：“午饭和同事吃面花了 68 元，微信支付。”模型可以整理成：

```json
{
  "category": "餐饮",
  "amount_cny": 68,
  "description": "和同事吃面",
  "payment_method": "微信支付",
  "date": null
}
```

这里 `date` 为空，是因为用户没有说明日期。应用可以采用当前日期，也可以再询问用户，不能让模型凭空补一个日期。

### 2. 从邮件、发票或订单文本中提取字段

例如从发票文字中抽取发票号码、日期、销售方和金额，方便录入财务系统：

```json
{
  "invoice_number": "INV-2026-0318",
  "issue_date": "2026-03-18",
  "seller": "示例科技有限公司",
  "total_cny": 1280.5
}
```

它像是让 AI 先替人读材料、填表，但正式入账前仍应核对原文和金额，尤其是涉及财务的数据。

### 3. 地址智能解析

用户粘贴：“张小明，13800138000，浙江省杭州市西湖区文三路 100 号 5 幢 201。”模型可以拆成表单字段：

```json
{
  "recipient": "张小明",
  "phone": "13800138000",
  "province": "浙江省",
  "city": "杭州市",
  "district": "西湖区",
  "detail": "文三路 100 号 5 幢 201"
}
```

程序随后把字段填进收件地址表单。姓名、电话和地址属于个人信息，应用应按需要使用并妥善保护；解析结果也应允许用户修改。

### 4. 意图分类与业务路由

用户说：“这个订单我不要了，想退款。”模型可以输出：

```json
{
  "intent": "申请退款",
  "order_id": null,
  "needs_follow_up": true,
  "missing_fields": ["order_id"]
}
```

程序读取 `intent` 后可以进入退款处理流程；发现订单号缺失，就先请用户补充。若用户说“帮我查物流”，模型可能输出 `intent: "查询物流"`，程序再转到物流查询流程。

这属于 Structured Output 与业务路由的配合：模型负责把自然语言整理成约定字段，程序根据字段执行明确的分支。输出 JSON 本身不会自动查询订单或退款。

### 5. 多轮对话中的参数补全

用户：“帮我查一下订单有没有发货。”模型判断还缺订单号，可以给程序一个结构化状态：

```json
{
  "action": "ask_user",
  "question": "请提供订单号，我来帮你查询物流。",
  "order_id": null
}
```

用户补充订单号后，系统把它保存到对话状态，再让模型或程序判断必填字段是否齐全。信息齐全时，程序才调用查询工具。这里的结构化输出让“缺什么、下一步做什么”变得可检查；对退款等有实际影响的操作，还应设置用户确认和权限校验。

### 6. 用户反馈分类与情绪整理

用户反馈：“客服态度不错，不过等了很久才收到货。”可以整理成：

```json
{
  "sentiment": "mixed",
  "positive_points": ["客服态度不错"],
  "issues": ["配送等待时间长"],
  "suggested_team": "物流"
}
```

企业可以据此做反馈统计或转给相关团队。它适合辅助分类和汇总，但单条模型判断不应被当作绝对客观的事实。

### 7. 会议纪要转成待办

从“周五前由小林发新版报价，王经理确认预算”中，模型可以提取：

```json
{
  "tasks": [
    {"owner": "小林", "task": "发送新版报价", "due_date": "周五"},
    {"owner": "王经理", "task": "确认预算", "due_date": null}
  ]
}
```

后续程序可以把它显示为待办列表。像“周五”这样的相对日期，需要结合会议日期换算；不确定时应保留原文或要求确认。

### 8. 把结果交给界面或其他程序

Structured Output 也常用于生成 UI 可直接展示的数据，例如搜索结果摘要、商品比较表或旅行计划卡片：

```json
{
  "title": "成都五日游",
  "highlights": ["美食", "市区景点"],
  "estimated_budget_cny": 8000,
  "needs_confirmation": true
}
```

前端可以读取这些字段来画卡片或表格，后端也可以把它们传给其他服务。模型负责产出符合格式的数据，界面怎么显示、数据是否保存，仍由应用程序负责。

## Structured Output 和 Tool Calling 的关系

两者常常连在一起，但不是一回事。Structured Output 是让模型按约定格式给出数据；Tool Calling 是应用根据模型给出的工具名称和参数，实际执行某个工具。例如模型输出“查询物流，订单号为 A123”，程序校验订单号后调用物流接口，再把结果交回模型组织语言。

可以把它们想成“填好一张格式固定的业务单”和“拿着业务单去办事”：前者提供可读、可检查的数据，后者才会触发实际动作。执行前仍要做参数校验、权限检查和必要的用户确认。

## 重要边界

Structured Output 主要约束**输出长什么样**，例如字段是否齐全、类型是否符合要求。它不自动保证模型提取的内容真实或正确，也不代表数据已经保存。

如果用户没有提供某项信息，系统可以把字段标为空、标记为缺失，或者继续询问。保存到数据库或生成文件，则由应用程序后续处理。

## 我的总结

> **Structured Output 就像 AI 辅助填写一份有固定表头和规则的模板：人用自然语言描述，模型按 Schema 整理成结构化数据，程序再校验并决定如何使用。**

它把“人容易表达的自然语言”和“程序容易处理的结构化数据”连接了起来。
