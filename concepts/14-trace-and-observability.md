# Trace 和 Observability：看懂 AI 应用是怎样运行的

在学习 AI Agent 时，我发现只看最后一句回答，往往无法判断系统到底哪里出了问题。模型可能识别错了意图，Router 可能走错了分支，State 可能没有更新，工具也可能调用失败。

这时就需要两个概念：**Trace** 和 **Observability**。

我最喜欢的类比是医院：

> **Trace 是某一次完整手术的记录；Observability 是一整套监控医院运行状况的系统。**

## Trace：一次请求的完整记录

假设用户说：

> 帮我查一下 A123 订单有没有发货。

这一次请求可能经过：

```text
接收用户输入
    ↓
解析意图和订单号
    ↓
Router 选择订单查询分支
    ↓
State 保存订单号
    ↓
Tool Calling 调用订单工具
    ↓
工具返回物流结果
    ↓
模型生成最终回答
```

Trace 会把这次请求经过的步骤串起来，并记录每一步的输入、输出、状态和耗时。例如：

```json
{
  "run_id": "run-4407",
  "status": "success",
  "steps": [
    {
      "name": "解析意图",
      "type": "model",
      "duration_ms": 428,
      "output": {
        "intent": "查询物流",
        "order_id": "A123"
      }
    },
    {
      "name": "选择分支",
      "type": "router",
      "duration_ms": 2,
      "output": {
        "branch": "order_lookup"
      }
    },
    {
      "name": "查询订单",
      "type": "tool",
      "duration_ms": 315,
      "output": {
        "shipping_status": "已发货"
      }
    }
  ]
}
```

如果最后答案错了，我们可以沿着 Trace 往回看：是意图解析错了，还是订单工具返回错了，或者模型没有正确使用工具结果。

## Span：Trace 里面的一个步骤

Trace 通常可以拆成多个 Span。一个 Span 就是一次处理环节，例如：

```text
Trace：查询订单 A123
├── Span：接收请求
├── Span：模型解析意图
├── Span：Router 分流
├── Span：State 更新
├── Span：调用订单工具
└── Span：生成最终回答
```

Span 通常会记录：

- 步骤名称
- 步骤类型
- 开始和结束时间
- 耗时
- 输入和输出
- 成功、等待或失败状态
- 错误信息
- 父步骤和子步骤关系

因此，复杂 Agent 即使不是一条直线，也可以通过 Trace 看出它的调用拓扑：它先走了哪个节点，又分出了哪些工具调用。

## Observability：整套系统的监控能力

Trace 只关注某一次请求，而 Observability 关注整个 AI 系统的运行状况。它通常包含几类数据：

```text
Observability
├── Logs：具体发生了什么
├── Traces：一次请求经过了哪些步骤
├── Metrics：整体表现怎么样
└── Alerts：出现问题时如何提醒
```

它像医院的整体监控系统：不仅保存某一台手术的过程，还要观察全院手术量、平均时长、失败率和异常情况。

## Logs：某个事件的记录

日志记录具体发生的事件，例如：

```text
订单工具调用失败
order_id=A123
error=请求超时
retry_count=1
```

在 AI 应用中，日志可以记录模型调用、Prompt 版本、工具参数、异常信息和重试过程。但日志通常是一条条事件，单独查看时不一定能还原完整请求；Trace 会负责把同一次运行的事件串起来。

## Metrics：整体统计指标

Metrics 是对大量请求做出的统计，例如：

```text
请求总数：1000
Agent 成功率：96%
平均响应时间：2.4 秒
工具调用失败率：3%
平均输入 Token：850
平均输出 Token：210
```

Metrics 适合回答“系统整体表现怎么样”。如果发现工具失败率突然升高，再通过 Trace 找出具体是哪类请求、哪一个工具出现问题。

## Alerts：发现异常后提醒

当指标超过某个范围时，系统可以发出提醒：

```text
工具调用失败率超过 10%
模型平均响应时间超过 8 秒
JSON 格式错误率连续升高
RAG 检索为空的比例异常
Agent 循环次数超过限制
```

Alerts 让维护人员不必一直盯着日志，而是在系统出现明显异常时及时处理。

## AI 应用要观察什么？

普通软件主要关注接口、数据库和服务器；AI 应用还要观察模型和 Agent 的行为：

- Prompt 使用了什么版本
- 模型识别出的意图是什么
- Router 选择了哪个分支
- State 如何变化
- Memory 是否被读取
- RAG 检索到了哪些资料
- Tool Calling 使用了哪个工具
- 工具传入了什么参数
- 工具返回了什么结果
- 使用了多少 Token
- 模型响应耗时多久
- 是否发生重试或循环
- 最终回答是否符合预期

例如一次查询物流的 Trace 可以是：

```text
用户输入
  ↓ 3 ms
意图解析
  ↓ 428 ms
Router 分流
  ↓ 2 ms
State 更新
  ↓ 2 ms
订单工具调用
  ↓ 315 ms
最终回答
  ↓ 121 ms
完成
```

## 失败时 Trace 如何帮助定位？

假设用户没有提供订单号：

```text
意图识别：通过
Router：通过，进入订单查询分支
State：发现缺少 order_id
工具调用：没有执行
最终状态：等待用户补充
```

这不是系统失败，而是一次正确的暂停。

如果用户提供了订单号，但工具服务超时：

```text
意图识别：通过
Router：通过
State：通过
工具调用：失败，服务超时
Retry：重试一次后仍失败
最终回答：说明暂时无法查询，没有编造结果
```

通过 Trace，我们可以区分：

- 模型理解错误
- Router 逻辑错误
- State 保存错误
- 工具参数错误
- 第三方服务故障
- 最终回答没有使用工具结果

如果只看最后一句“查询失败”，很难知道具体原因。

## Trace 和 Evals 的关系

这两个概念经常一起使用，但关注点不同：

- **Evals**：这条测试是否符合期望，适合统计通过率。
- **Trace**：这次运行具体经过了哪些步骤，适合定位问题。
- **Observability**：把 Trace、Logs、Metrics 和 Alerts 组织起来，持续观察整个系统。

可以这样记：

```text
Evals：这台手术合格吗？
Trace：这台手术每一步是怎么做的？
Observability：整个医院最近运行得怎么样？
```

## 我的总结

> **Trace 是一次 AI 请求的结构化操作记录；Observability 是观察整个 AI 系统运行情况的能力。Logs 记录事件，Trace 串起链路，Metrics 统计整体表现，Alerts 提醒异常。**

对于 AI Agent 来说，可观测性非常重要。只有看见模型、Router、State、RAG 和工具调用的中间过程，我们才能知道系统为什么成功，也才能在失败时快速找到真正的问题。
